# Поиск и LLM-уточнения — контракт MVP

Актуальное требование владельца: «Умный поиск» — переключатель. По умолчанию
выключен; кнопка отправки всегда «Найти». Переключатель и вопрос находятся в одном
блоке со строкой поиска. Это заменяет прежний обязательный онбординг и выбор
статических вопросов локальными правилами.

В интерфейсе используется нейтральное название «Прототип»: без логотипа и названия
«Альфа Курс», без подписи Hack&Change. Реальные названия материалов и ссылки каталога
сохраняются; кнопка перехода подписана «Открыть материал».

## Два режима

- normal: TF-IDF по названию (усилен двойным вхождением), аннотации и темам.
  Словарь включает одиночные термины и не обрезается до 8000 слов. Это отдельный
  индекс поиска; прежний сохранённый TF-IDF рекомендателя сохраняет свои настройки.
  До 20 результатов с ненулевым совпадением; пустая строка показывает каталог.
  Нет чтения профиля для ранжирования, семантического encoder и любых LLM-вызовов.
  Изученный материал может остаться в обычных результатах поиска.
- smart: локальные семантические рекомендации с историей. LLM решает, нужен ли
  наводящий вопрос, когда локального контекста недостаточно, и сама формулирует
  вопрос и 2–5 вариантов ответа. Тематика уточнения не ограничена stage/goal/format.
  Достаточный контекст (конкретная распознанная задача или выбранная цель)
  не уточняется повторно: assistant_status=not_needed, question=null.
  Один формат или стадия бизнеса без задачи не заменяют цель: LLM-уточнение доступно.
  Совпадение общего глагола с названием карточки («как выбрать», «нанять») также
  не определяет задачу: для пропуска вопроса нужна распознанная бизнес-тема и объект.
  Это эвристика, не универсальный классификатор намерений. Конкретная задача не должна требовать
  лишнего онбординга; общую задачу следует уточнить. Ответ меняет вход ранжирования.
  Стадия/цель/формат не записываются как устойчивые интересы без события.

Для непустой задачи кандидаты определяются до смешивания с историей: запрос 90%,
история 10%, темы только текущей задачи. «ИИ/AI/нейросети» разрешаются в метку
«ИИ и автоматизация». Один явно запрошенный формат фильтрует выдачу; выбранный
ответ о формате имеет приоритет. Пустая задача сохраняет персонализацию.
Подробности и дополнительные параметры /recommend: [search-intent-priority.md](search-intent-priority.md).

## HTTP

POST /search — основной адрес, search_mode=normal по умолчанию.
POST /smart-search — совместимый адрес, search_mode=smart по умолчанию.
POST требует Content-Type: application/json (допустим charset); иначе 415.
Браузерный Origin должен совпадать с локальным HTTP-сервисом по Host, включая порт;
чужой/null Origin или стороннее DNS-имя → 403 до вызова модели и записи состояния.
Проверка Origin действует также на DELETE. CLI без Origin поддерживается.
Это защита локального демо от сторонних страниц, не авторизация пользователей.
Для выбора синтетических ролей есть отдельная cookie-сессия [demo-login.md](demo-login.md):
сервер привязывает поиск/события к её профилю и отклоняет подмену ID. Истинную
личность пользователя платформы этот общедоступный демовход не проверяет.
Вход — JSON-объект по [smart-search.schema.json](smart-search.schema.json):

- task: строка до 2000 символов, пустая допустима;
- profile_id: anon:token или user:pseudonym, необязателен;
- search_mode: normal|smart;
- answers: stage=beginner|owner|growth; goal=launch|marketing|finance|team|operations;
  format=overview|tool|course. Прежний enum-контракт оставлен для совместимости;
- clarifications: до двух подписанных токенов из question.options[].value.
  Новый интерфейс использует их вместо answers. Подмена/просрочка/перенос на другой
  запрос/другая последовательность выбора → 400 до LLM и ранжирования;
- skip_questions: bool, подавляет LLM-уточнение;
- industry/experience: строки до 200 символов, остаются локальными;
- use_llm: bool, прежняя необязательная проверка карточек. В normal игнорируется;
  в smart проверка карточек отдельна от автоматического LLM-уточнения.

Неверные типы/значения, неизвестные поля → 400. Ответ: items, summary, search_mode,
match_status, question|null, question_source, context_sufficient, assistant_status.
В smart остаются mode/backend/factors/profile_topics из рекомендателя; в normal
возвращается total_matches. question_source=cloud_llm только после валидного ответа
модели; без вопроса null. assistant_status описывает именно LLM-уточнение,
включая already_answered при подавлении повтора известного параметра;
llm_status — старую отдельную проверку карточек. dialogue содержит проверенные
пары question/answer для боковой панели. Токены действуют один час в одном процессе
API; перезапуск требует начать диалог заново. Подробности: [dynamic-clarifications.md](dynamic-clarifications.md).

## LLM и минимизация данных

reco/clarification.py использует общий structured_call из llm_cloud.py:
OpenRouter/совместимый HTTPS API, LLM_PROVIDER/API_KEY/MODEL/BASE_URL, без redirects
и транспортных повторов, timeout 30 с, до 900 выходных токенов на вызов. OpenRouter требует поддерживаемый
маршрут с data_collection=deny, zdr=true и require_parameters=true; ограничения
провайдера и Safety Retention описаны в README. Ollama для вопросов не реализована.

В облако идут фиксированные бизнес-темы/действия, hint general/unknown, булев
признак наличия истории, доступные типы форматов и legacy preferences из констант.
Также передаются request_focus — фокус текущего запроса, и profile_topics — до трёх
обобщённых бизнес-тем профиля. Оба поля содержат только локальные константы.
Фокус должен быть назван в title. При его потере допускается одна дополнительная
генерация с константной validation_feedback, без отправки отвергнутого ответа.
Повторная потеря темы → topic_mismatch, вопрос не показывается, выдача сохраняется.
Опечатки «искуственный интеллект»/«искуственый интелект» распознаются локально.
Подробности: [clarification-context.md](clarification-context.md).
Для следующего вопроса передаются только фиксированные бизнес-признаки прежних
пар: темы, канал, уровень, формат и укрупнённый диапазон бюджета. Строки вопроса/
выбранного ответа и исходные числа остаются локально. Их происхождение подтверждается
подписью; свободный клиентский текст не принимается, токены наружу не отправляются.
Нет исходного текста запроса, имён/контактов, UUID/profile_id, самой истории, каталога,
аннотаций, закрытых текстов и векторов. Локальная оценка достаточного контекста
предотвращает повторное уточнение. При недостаточном контексте LLM получает hint
general/unknown и решает, нужен ли вопрос. Цена минимизации — LLM не видит всех нюансов
исходного запроса. Она работает с безопасной проекцией; это явно указано в интерфейсе.

Ответ модели: needs_clarification:boolean и question|null, схема
[llm-clarification.schema.json](llm-clarification.schema.json). Для вопроса нужны
сгенерированный title и 2–5 options[{label,preferred_format}]. Все видимые варианты
пишет модель под свой вопрос. Формат — только существующий тип каталога либо пусто.
Проверяются форма, длина, дубли, HTML/ссылки/запрос контактов. Повтор того же title
отклоняется; универсальная смысловая проверка соответствия не реализована.
Клиент получает подписанный value на каждый label. Максимум два уточнения.

Пустая строка, пропуск или два ответа не вызывают LLM-уточнение. При отсутствии
ключа, сбое HTTP/JSON, тайм-ауте или неподдерживаемом провайдере вопрос не показывается,
статического fallback нет. Интерфейс сообщает о недоступности LLM и оставляет
локальную подборку. Ключ не попадает в браузер. Реальная облачная интеграция без
ключа не выдаётся за проверенную; контракт тестируется с подставленным ответом.

## Каталог, история и интерфейс

Только существующие eligible ID. Объяснение основано на каталоге; следующий материал
берётся из той же выдачи, его порядок — предложение, не доказанная зависимость.
Незавершённый положительный материал в smart может вернуться с пометкой «Продолжить»
и бонусом .03; завершённые/отрицательные/закрытые исключены. Прежний /recommend
сохраняет исключение просмотренных по умолчанию (include_continuations=false).

Нет стандартизированной сложности: duration/target/lesson_quantity только из источника.
Q&A-2: тело статьи только Public TypeId и !IsClosed; IsPublic — редакторский флаг.
CourseUserBindings.ContentAccess 1/2 — доступ, 0/10 не владение и не покупка.
Подробности миграции индекса — README и docs/requirements-audit.md. В этом уточнении
режимов схема PostgreSQL и fingerprint индекса не меняются, пересборка не нужна.

GET / — HTML, /health — JSON; JS/CSS по allowlist. Каталог выводится как текст,
превью содержит только аннотацию. Гостевой случайный ID — в localStorage; запрос и
ответы — в памяти вкладки. Есть удаление агрегата профиля. Открытие превью и явные
«Полезно»/«Изучил»/«Не подходит» обновляют ограниченный профиль с TTL. Это не замер
активного времени на внешней платформе. События отправляются последовательно.

## Проверки

Обычный режим без LLM/персонализации, переключение и сброс ответов, пустая выдача,
невалидный вход; LLM формулирует вопрос либо решает его не задавать; ответ меняет
выдачу; проверка исходящего payload на ПДн; ошибки модели и лимит/повтор вопросов;
настоящая тестовая PostgreSQL, браузерная проверка и короткий живой OpenRouter-сценарий.
