# Хранение состояния в PostgreSQL

По уточнению пользователя PostgreSQL — единственная БД проекта. Служебный SQLite
убирается из исполнения. Доступ задаётся обязательной переменной DATABASE_URL.

В отдельной схеме reco хранятся профили (JSONB, сроки жизни, идентификатор индекса),
история обучения и маркеры импорта. Исходные таблицы public не изменяются.
Гостевой TTL, абсолютный срок, предел числа гостей на индекс, лимиты материалов/event_id,
дедупликация и объединение после входа сохраняются. Обновления атомарны;
одновременное создание профилей не должно обходить лимит гостей.

История и профили разделены по fingerprint индекса. Переимпорт истории заменяет
только данные соответствующего индекса в одной транзакции. Ошибка откатывает импорт.
У PostgreSQL нет встроенного TTL: сервер приложения удаляет просроченные профили
раз в минуту и при записи; чтение сразу игнорирует истёкшие данные.

Совместимость: HTTP/CLI-контракты сохраняются. Старые файлы индекса и модели
переиспользуются; история восстанавливается из исходного backup в PostgreSQL.
Существующие SQLite-файлы не удаляются и автоматически не читаются. Старые
временные демо-профили не переносятся; новые события формируют новые профили.
Откат — возврат предыдущей версии кода и её сохранённых локальных файлов.

Проверки: настоящий изолированный PostgreSQL, истечение TTL, абсолютный срок,
предел гостей, параллельные записи, изоляция индексов, объединение, атомарность
импорта и рекомендации по сохранённой истории. Рабочая БД не используется в тестах.

## Исправления после независимого ревью

Новый индекс собирается в отдельном неизменяемом поколении `.generations/`.
Указатель `current` переключается атомарно только после успешного импорта history
и записи manifest с контрольными суммами. Неуспешная сборка не меняет рабочее поколение.
Чтение фиксирует одно поколение на всю загрузку и проверяет fingerprint каталога/encoder;
для новых поколений проверяются также суммы всех файлов.
Старые плоские индексы поддерживаются, несогласованный fingerprint отвергается.
Все потребители, включая startup и migrate, используют один resolver.

CLI cleanup использует только PostgreSQL, без файлов индекса, модели и marker history.
Глобальный продуктовый sweep сохраняется. Его тест выполняет реальный SQL внутри
rollback-only транзакции на заимствованном соединении: удаление проверяется до отката,
а посторонние fixtures после теста сохраняются.
