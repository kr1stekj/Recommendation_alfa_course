# Альфа-Курс: персональные рекомендации

Python-прототип первого трека хакатона: подбирает образовательные материалы по
задаче предпринимателя, истории обучения и новым взаимодействиям. Показывает
основание выбора и следующий шаг. Есть веб-интерфейс «Умного поиска», CLI и JSON API.
Название в интерфейсе — «Прототип».

Актуальная обзорная документация: [TECHNICAL_GUIDE.md](docs/TECHNICAL_GUIDE.md).
Статусы старых экспериментов ниже относятся к их исходным версиям.

**Проверка требований:** [аудит первого трека](docs/requirements-audit.md).
Основной пользовательский сценарий реализован; ограничения оценки, Docker и живой LLM
перечислены в аудите.

**Основная модель — `BAAI/bge-m3` для локальных эмбеддингов.** Рекомендации
работают без генеративной LLM. В умном режиме LLM через облачный API формулирует
уточнения; отдельно доступна проверка карточек через OpenRouter/совместимый
Chat Completions сервис. Ollama сохранена для дополнительной локальной проверки.
Профили и история хранятся в PostgreSQL; каталог, векторы и модель — в файлах.

## 1. Быстрый запуск через Docker

Нужны Docker Engine с Compose, доступ к интернету для первой сборки и предоставленный
организаторами `alfa_course_hackathon.backup`. Сам дамп в репозиторий не входит.

Из корня проекта:

На Windows используйте Docker Desktop с Linux containers/WSL 2 и PowerShell:

```powershell
New-Item -ItemType Directory -Force data | Out-Null
Copy-Item "C:\путь\к\alfa_course_hackathon.backup" "data\alfa_course_hackathon.backup"
if (-not (Test-Path .env)) { Copy-Item env.example .env }
$env:EMBEDDING_DEVICE = "cpu"
docker compose up --build
```

Команда сохраняет существующий `.env` с ключом/паролем. Нужны запущенный Docker Desktop и доступ к сети для
первого скачивания. Установка Python/PostgreSQL на Windows-хосте не требуется.
Подготовку WSL 2 описывает [официальная инструкция Docker](https://docs.docker.com/desktop/setup/install/windows-install/).

На macOS/Linux:

```bash
mkdir -p data
# Замените путь на расположение полученного файла:
cp "/путь/к/alfa_course_hackathon.backup" data/alfa_course_hackathon.backup

docker compose up --build
```

Compose запускает PostgreSQL 17, ожидает её готовности, восстанавливает индекс из
готовых векторов в репозитории и импортирует историю из вашего `.backup`, затем
поднимает API. Повторная векторизация каталога по умолчанию не нужна. Первый запуск
скачивает зависимости и веса модели для новых поисковых запросов; дождитесь
сообщения `Local demo API`.

- **Интерфейс: <http://127.0.0.1:8000/>.**
- Состояние API: <http://127.0.0.1:8000/health>.
- PostgreSQL с хоста: `localhost:5433`, БД `reco`, пользователь `reco`.
- Локальный демонстрационный пароль по умолчанию: `local-demo-only`.
- Внутри Compose сервер БД: `postgres:5432`.
- Данные БД остаются в томе `postgres_data`, индекс — `reco_artifacts`, веса — `reco_models`.

Docker запускает **CPU-вариант** на Windows/macOS/Linux; MPS — только опция локального
Python на Apple Silicon. По умолчанию ни CUDA, ни Apple GPU не требуются. Индекс и
кеш хранятся в управляемых Docker Linux-томах, чтобы символьные ссылки и атомарное
переключение поколений не зависели от NTFS/Developer Mode Windows.
[Назначение томов Docker](https://docs.docker.com/engine/storage/volumes/).
Локальные Python-команды по-прежнему используют host-папки `artifacts/`, `models/`.
После обновления Compose старые host-папки не удаляются, но новый контейнер восстанавливает
индекс в своих томах и скачивает модель один раз. Запуск без Docker на Windows
отдельно не проверен; поддерживаемый путь для проверки — контейнеры.

Готовые матрицы занимают около **4,5 МиБ** и приходят с `git pull`. Восстановление
не вызывает encoder; каталог и история берутся из исходного дампа локально.
Веса BGE всё ещё нужно скачать один раз — около 2,3 ГБ, поэтому первый старт зависит
от скорости сети. Выделите Docker несколько ГБ RAM; при нехватке памяти уменьшите
`EMBEDDING_BATCH_SIZE` до 1–2. Прогресс виден в логах.
Healthcheck имеет 60 минут стартового окна, но становится healthy сразу после
готовности API — это не обязательная задержка. Последующие старты используют кеш.

Если ранее экспортировали `DATABASE_URL` для Python на хосте, он переопределит
внутренний адрес Compose. Для штатной контейнерной БД запускайте:

```bash
env -u DATABASE_URL docker compose up --build
```

Проверьте также, что в локальном `.env` не задан адрес БД хоста вместо `postgres:5432`.
Шаблон настроек — [env.example](env.example). Рабочие пароли в Git не добавляйте.

Проверка в другом терминале:

```bash
curl http://127.0.0.1:8000/health
```

В PowerShell: `Invoke-RestMethod http://127.0.0.1:8000/health`. В ответе доступны
`embedding_model`, `embedding_device`, `vector_dimension`; ожидаются BAAI/bge-m3,
cpu, 1024. Логи: `docker compose logs -f recommender`.
Сквозная проверка после готовности API: `docker compose exec recommender python scripts/smoke_api.py`.
Она создаёт только своего тестового гостя, проверяет выдачу/события и удаляет его.

Демо с теми же контейнерными настройками:

```bash
docker compose exec recommender python -m reco.cli demo
```

Для остановки — `Ctrl+C`, затем `docker compose down`. Том БД при этом сохраняется.
Сборка и запуск контейнеров пока не подтверждены на этой машине: Docker Engine
был недоступен. `docker compose config --quiet` проверяет конфигурацию, но не заменяет запуск.
Фактический запуск на Windows также ещё не подтверждён; Mac/MPS-проверка его не заменяет.

## 2. Запуск Python локально

Нужны Python 3.9–3.11, PostgreSQL 17 и `pg_restore` версии 17 или новее в `PATH`.
БД приложения должна уже существовать; пользователь должен иметь право создавать
служебную схему и таблицы. Можно использовать свою локальную PostgreSQL либо только
сервис БД из Compose:

```bash
docker compose up -d postgres
docker compose exec postgres pg_isready -U reco -d reco
```

Дождитесь `accepting connections`. Затем в корне проекта:

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

# Для БД из Compose; для своей БД замените строку подключения.
export DATABASE_URL='postgresql://reco:local-demo-only@localhost:5433/reco'
pg_restore --version

python -m reco.precomputed restore --backup data/alfa_course_hackathon.backup
python -m reco.model_cache
python -m reco.cli demo
```

Для веб-интерфейса после восстановления индекса и подготовки кеша:

```bash
python -m reco.server
```

Откройте <http://127.0.0.1:8000/>. «Умный поиск» — **переключатель**, по умолчанию
выключен. Введите запрос и нажмите «Найти».

- Выключен: обычный поиск TF-IDF по словам в названии, аннотации и темах;
  учитывает и термины единственной карточки. Без персонализации, вопросов и LLM-вызовов.
- Включён: семантические рекомендации с историей. Распознанная конкретная задача
  или выбранная цель не уточняются повторно (`assistant_status=not_needed`).
  Если локального контекста недостаточно, LLM решает, нужен ли вопрос, и формулирует
  вопрос и варианты ответа у строки поиска. После ответа
  подборка обновляется. Вопрос можно пропустить; максимум два уточнения.

Вопросы и видимые варианты полностью формулирует LLM; готовых списков ответов в
интерфейсе нет. Выбранная пара «вопрос + ответ» уточняет локальную векторизацию и
темы выдачи. Она живёт только в диалоге страницы. Старый API `answers` поддержан
для совместимости; новый интерфейс передаёт `clarifications` из ответа сервера.

Карточки показывают
аннотацию, причину выбора, ID/ссылку и следующий материал. «Посмотреть» сохраняет
click; «Полезно», «Уже изучил», «Не подходит» — явную обратную связь. Незавершённый
материал может вернуться с меткой «Продолжить». В боковой панели можно указать
сферу/опыт и удалить гостевую историю. Случайный ID хранится в localStorage,
поисковая строка и ответы на вопросы — только в памяти страницы.

### Проверка синтетических пользователей

Нажмите **«Войти»** в шапке и выберите готовый демопрофиль. Регистрация и пароль
не нужны. Доступны: новый пользователь без истории, начинающий предприниматель,
маркетинг/продажи, налоги/маркетплейсы, управление командой и финансы.

Вход включает умный режим и показывает подборку по тестовым интересам. У ролей
до трёх синтетических стартовых действий с доступными материалами; у нового
пользователя их нет. События строятся по меткам текущего каталога, без реальных
пользовательских ID и без использования оценок из `evaluation/profiles.json`.
Обычный режим можно включить переключателем и сравнить результаты.

- Обновление страницы восстанавливает текущую сессию и умный режим.
- **«Сбросить демопрофиль»** возвращает исходные тестовые действия.
- Кнопка с названием профиля позволяет выбрать другую роль — это новая копия.
- **«Выйти»** удаляет текущую тестовую копию и возвращает прежнего гостя браузера.

Копии изолированы между браузерами и входами. Гостевые события не переносятся.
Сессия хранится на сервере, cookie — HttpOnly/SameSite=Strict, срок один час,
максимум 512 сессий на процесс. После перезапуска нужно войти заново. Демоагрегаты
используют существующую `reco.profiles` и гостевой TTL; исходная история backup
не меняется. Это выбор общедоступной тестовой роли, не проверка личности реального
пользователя платформы. Контракт — [specs/demo-login.md](specs/demo-login.md).

Для вопросов настройте `LLM_PROVIDER`, `LLM_API_KEY`, `LLM_MODEL` по разделу 6
и перезапустите сервер. Без ключа/при ошибке умный режим явно сообщает о недоступности
LLM и показывает локальную подборку **без подставных статических вопросов**.
Пустая строка не вызывает LLM. Ответы влияют на эмбеддинг и предпочтение формата.
Контракт — [specs/smart-search.md](specs/smart-search.md).

После обновления с версии до Q&A-2 **один раз восстановите актуальный индекс** командой
`python -m reco.precomputed restore --backup data/alfa_course_hackathon.backup`: уточнены доступ,
владение курсом и метаданные. Старое поколение сохраняется для отката, profile_id
между fingerprint не переносится. Затем перезапустите сервер.

На Apple Silicon, если PostgreSQL 17 установлена через Homebrew, путь к утилитам
можно добавить так: `export PATH="/opt/homebrew/opt/postgresql@17/bin:$PATH"`.
Пароль с особыми символами в `DATABASE_URL` нужно кодировать как часть URL.

`DATABASE_URL` требуется в каждом новом терминале. Python-команды сами `.env`
не загружают. Индексацию не нужно повторять при каждом запуске.

В `demo`:

1. Без задачи показывается общая стартовая подборка.
2. Введите `?Как управлять командой и нанимать сотрудников` — изменится текущая задача.
3. Введите номер карточки — будет отправлено **синтетическое** событие `engaged`.
4. Новая выдача учтёт событие и исключит просмотренный материал.
5. `q` — выход. Для продолжения с тем же профилем передайте напечатанный `--profile anon:...`.

Один запрос с ответом JSON:

```bash
python -m reco.cli recommend \
  --task 'Как управлять командой и нанимать сотрудников' \
  --topic 'Управление командой' --format course -k 5
```

`--format` — предпочтение, а не жёсткий фильтр. Допустимы `article`, `course`,
`document`, `podcast`. Необязательный онбординг: `--stage`, `--industry`, `--experience`.
Темы задаются повторяемым `--topic`. Зарегистрированный профиль: `--profile user:<UserId>`.
В публичном демо используйте искусственные идентификаторы.

### TF-IDF вместо нейросетевого encoder

Лексический режим не скачивает нейросетевую модель. Он сравнивает взвешенные слова:

```bash
python -m reco.build --backup data/alfa_course_hackathon.backup \
  --backend tfidf --output artifacts-tfidf
python -m reco.cli demo --artifacts artifacts-tfidf
```

Минимальные зависимости для этого режима: `numpy==2.0.2` и `psycopg[binary]==3.2.4`.
Автоматического переключения на TF-IDF при сбое нейросети нет. Не смешивайте backend
одного индекса; для сравнения используйте разные папки.

### Готовые эмбеддинги для команды

Набор [precomputed/bge-m3/](precomputed/bge-m3/) рассчитан на исходном дампе
организаторов, моделью BGE-M3 с контекстом 512, на дату **2026-11-15**. Это две
числовые матрицы (1126 материалов × 1024 и 26 тем × 1024), настройки encoder и
manifest с SHA256. Тексты, ID материалов, история пользователей и веса в набор
не входят. Каталог восстанавливается из вашего `.backup` в точном порядке строк;
исходный fingerprint и разделение профилей сохраняются.

При пустом Docker-томе `USE_PRECOMPUTED_EMBEDDINGS=1` включён по умолчанию.
Существующий корректный индекс используется как раньше. Если дамп, модель,
длина контекста или контрольные суммы не совпадают, запуск завершается с ошибкой,
без скрытого долгого пересчёта. Для другого дампа/модели явно задайте
`USE_PRECOMPUTED_EMBEDDINGS=0` в `.env`; эта настройка строит индекс при пустом томе.
Существующий индекс меняется только явной командой восстановления или сборки.

Чтобы заменить прежний индекс в Docker-томе готовыми векторами:

```bash
docker compose stop recommender
docker compose build recommender
docker compose run --rm recommender python -m reco.precomputed restore \
  --backup /data/alfa_course_hackathon.backup
docker compose up -d recommender
```

БД и старые поколения сохраняются. Нативный restore принимает `--artifacts`,
а `python -m reco.model_cache --artifacts ...` подготавливает файлы модели для
этого индекса. В готовом кеше сеть не нужна; на полностью offline-машину кеш
нужно перенести отдельно. Восстановленные векторы работают на CPU и MPS.

Если каталог действительно изменился, сначала выполните обычную полную сборку,
затем экспортируйте новый набор в отдельную папку:

```bash
python -m reco.build --backup data/alfa_course_hackathon.backup
python -m reco.precomputed export --backup data/alfa_course_hackathon.backup \
  --bundle precomputed-new/bge-m3
```

Export не вызывает модель и не перезаписывает существующий набор. Публикуйте
только четыре проверенных файла набора; дополнительные `.npy` по-прежнему
игнорируются Git. После обновления bundle повторно проверьте restore из исходного
дампа. Контракт: [specs/precomputed-embeddings.md](specs/precomputed-embeddings.md).

### Готовый индекс и новая БД

Если индекс уже рассчитан, а в PostgreSQL ещё нет его истории, пересчёт векторов не нужен:

```bash
python -m reco.migrate --backup data/alfa_course_hackathon.backup
# Для лексического индекса:
python -m reco.migrate --backup data/alfa_course_hackathon.backup --artifacts artifacts-tfidf
```

Для обновления каталога или применения новых правил очистки запускайте `reco.build`.
После публикации нового индекса перезапустите API: работающий процесс держит своё
поколение в памяти. Профили разделены по fingerprint; старые интересы автоматически
в новое поколение не переносятся.

## 3. Что происходит с .backup

```text
alfa_course_hackathon.backup
  → pg_restore извлекает COPY-данные как текст
  → очистка каталога и связей
  → эмбеддинги материалов и центроиды тем
  → файлы нового поколения индекса
  → импорт истории в PostgreSQL, схема reco
  → атомарное переключение artifacts/current
```

`reco.build` работает именно с предоставленным `.backup`, SQL дампа не исполняет
и исходные таблицы `public` не создаёт и не изменяет. PostgreSQL здесь хранит
производную историю и профили приложения. Для отдельного аудита дамп дополнительно
восстанавливали через `pg_restore -d` в изолированную БД — это отдельная проверка,
не обязательный этап запуска рекомендателя.

В предоставленном дампе 62 таблицы, 102128 строк. В проверке от 14 ноября 2026:

Правила подготовки:

- Черновики, удалённые, будущие публикации и карточки без Id/названия/URL исключаются.
  Закрытые материалы остаются только для представления истории, в выдачу не попадают.
- HTML, скрипты, лишние пробелы и смешение похожих латинских/кириллических букв очищаются.
- SQL-маркер `\N` становится `None`; буквальный текст `\\N` декодируется отдельно.
  `NaN`/строка `nan` и числовые бесконечности в текстах превращаются в пустую строку.
- Отсутствующие PK/FK не соединяются друг с другом. Удалённая метка может стать алиасом
  живой только при совпадении нормализованного ключа.
- Настоящий `Courses.Cost=NULL` означает бесплатный курс по разъяснению кейса.
  Некорректная/NaN/отрицательная/дробная цена — неизвестная, в JSON `null`.
  На другие типы материалов правило бесплатности не переносится.
- Тексты уроков не индексируются; завершённые уроки усиливают сигнал истории курса.
  По Q&A-2 тексты статей берутся только при Public `TypeId` и `IsClosed!=true`;
  `IsPublic` — редакторский флаг, а не доступ. Закрытое содержание
  платных уроков не передаётся модели или пользователю.
- `UserRatings` пока только аудируются: шкалы оценок требуют проверки. В дампе
  6018 оценок без UserId — они не объединяются в одного гостя.
- В дампе нет журнала активного времени на страницах или кликов анонимных гостей.
  Даты начала/завершения обучения не равны фактическому времени просмотра.

## 4. Как выбираются материалы и темы

### Представление текста

По умолчанию используется [BAAI/bge-m3](https://huggingface.co/BAAI/bge-m3):
готовый мультиязычный encoder, 1024 координаты, CLS pooling и L2-нормализация.
Revision закреплена: `5617a9f61b028005a4858fdac845db406aefb181`; лицензия MIT.
Модель не дообучается. Здесь используется **dense**-ветка, без sparse/ColBERT и
отдельного reranker. Эти возможности модели не включаются автоматически.
Сборка или `reco.model_cache` скачивает веса в `models/huggingface`; тексты из дампа в сеть не отправляются.
Сохранённый индекс фиксирует revision модели и при запросах использует локальный кеш.
Вход по умолчанию обрезается до **512 токенов**, поэтому название и аннотация стоят
в начале. Нативный предел BGE-M3 — 8192; больший лимит можно задать при сборке,
но на 8 ГБ RAM он потребует отдельной проверки памяти и скорости. Batch по умолчанию 4.

Настройки Compose: `EMBEDDING_MODEL=BAAI/bge-m3`, `EMBEDDING_MAX_LENGTH=512`,
`EMBEDDING_BATCH_SIZE=4`, `EMBEDDING_DEVICE=cpu`. Первая загрузка весов — около 2,3 ГБ;
кеш сохраняется в `models/`. Официальная revision содержит `pytorch_model.bin`:
загрузка идёт с `weights_only=true` в PyTorch 2.6, без remote code и с
`low_cpu_mem_usage=true` (accelerate), чтобы не держать две полные копии модели.

После обновления с ruBERT восстановите BGE-индекс готовой командой выше.
Для самостоятельного расчёта из исходного backup:

```bash
python -m reco.build --backup data/alfa_course_hackathon.backup \
  --model BAAI/bge-m3 --max-length 512 --batch-size 4
```

На Apple Silicon для разовой сборки доступно `--device mps`; ускорение относительно
CPU для всего каталога не измерено. Runtime по умолчанию остаётся CPU.
Для MPS при запросах экспортируйте `EMBEDDING_DEVICE=mps` до запуска
сервера. CPU-контейнер не требует MPS, устройство не меняет пространство векторов.
`audit.json.embedding_device` показывает устройство **сборки**, а `/health.embedding_device`
— текущее устройство исполнения. Значение mps в старом audit не требует Mac для запуска.
При недоступном MPS возникает явная ошибка, скрытого переключения устройства нет.

Для существующих Docker-томов, пока основной сервис отклоняет старый индекс:

```bash
docker compose build recommender
docker compose run --rm recommender python -m reco.precomputed restore \
  --backup /data/alfa_course_hackathon.backup
docker compose up --build
```

Новая размерность — 1024 вместо 312; старые векторы не смешиваются с новыми.
Сборка создаёт новое поколение, старое сохраняется для отката. Меняется fingerprint:
история из backup импортируется заново для нового dataset, гостевые агрегаты между
версиями не переносятся. После сборки **перезапустите API**. Startup отказывается
молча использовать индекс другой модели/длины. Прежний encoder доступен явно через
`--model cointegrated/rubert-tiny2`; у него по-прежнему 312 координат и предел 512.
Другие имена моделей требуют адаптера, а не подстановки в CLS-код.

Контракт миграции: [specs/bge-m3.md](specs/bge-m3.md). Для измерения текущего индекса:

```bash
python scripts/benchmark_embeddings.py --artifacts artifacts \
  --device cpu --output artifacts/benchmark.json
```

Замер использует пять известных seed-профилей, измеряет короткие запросы после
прогрева и не доказывает производительность длинных текстов или production-нагрузки.
Цифры из сторонних тестов на другом CPU/GPU не являются результатом этого проекта.
Альтернатива — TF-IDF со словарём до 8000 слов; это лексическое представление.

Ненулевые векторы нормализуются к длине 1. Поэтому `vectors @ user_vector` даёт
косинусную близость сразу ко всему каталогу. NaN/Infinity в координатах при
нормализации заменяются нулями. Сохранённый индекс с нечисловыми координатами
отвергается даже при совпавших контрольных суммах. Нулевой вектор остаётся нулевым.

### Профиль и ранжирование

Сначала собирается взвешенный вектор истории. Для текущей задачи:

```text
user_vector = normalize(0.75 × query_vector + 0.25 × normalize(history_vector))
```

Без истории берётся запрос, без запроса — история. Без обоих используется общий
стартовый запрос с темами первых шагов. Если encoder вернул ноль, используются
центроид доступных материалов выбранных меток, стартовый текст, затем средний вектор
доступного каталога; при пустом/нулевом каталоге вектор остаётся нулевым.
При наличии задачи и контекста онбординга
`query_vector = normalize(0.85 × task_vector + 0.15 × context_vector)`:
длинный общий контекст не должен перевешивать конкретную задачу. Это эвристика,
а не отдельный проверенный классификатор уровня сложности.

| algorithm | Что определяет порядок |
|---|---|
| `topic` | Доля совпавших выбранных/исторических тем; при равенстве — число записей на курс |
| `cosine` | Только близость векторов |
| `hybrid` — по умолчанию | Близость, темы, формат, популярность, отрицательная обратная связь |

Эти правила применяются к semantic или TF-IDF индексу: так получаются пять методов
в сравнении (тематический бейзлайн одинаков по смыслу для обоих backend).
Даже `topic` сейчас проходит общую подготовку запроса, поэтому semantic-индексу
для такой команды также нужен кеш encoder.

```text
score = 0.75 × clip(cosine, 0, 1)
      + 0.16 × topic_match
      + 0.04 × preferred_format_match
      + 0.05 × normalized_log_enrollment_count
      − 0.12 × similarity_to_dislikes
      + 0.03 × continuation
```

Это `hybrid-v2`: все шесть признаков конечны и лежат в `[0, 1]`, сумма четырёх
основных положительных весов — 1. Нулевой/отрицательный косинус не создаёт
положительный вклад. Поле `cosine` и baseline `algorithm=cosine` сохраняют исходную
шкалу `[-1, 1]`; пороги слабого совпадения также используют исходный косинус.
`topic_match` — доля совпавших меток каталога, не повторное сравнение эмбеддингов.
Векторные рекомендации тем не используются как `topic_match`.

Нет dislikes → штраф 0. Нет выбранного формата → его вклад 0. Отсутствующее,
неверное, отрицательное или неограниченное число записей → популярность 0;
корректные счётчики нормируются как `log(1+n)/max(log(1+n))`, все нули → нули.

Далее hybrid мягко штрафует похожие уже выбранные карточки и повтор формата
внутри отобранного пула кандидатов. Отрицательная близость не даёт бонус разнообразия.
Просмотренное и уже доступные по истории курсы
исключаются в обычном `/recommend`. «Умный поиск» передаёт `include_continuations=true`:
незавершённый положительный материал может вернуться, с бонусом 0.03 в hybrid.
Завершённые и отрицательные остаются исключёнными. Доступ по истории: ContentAccess
1/2; пробная запись 0 или отозванный доступ 10 не являются владением.
Популярность сейчас есть только у курсов; это записи на курс, не покупки.
Веса ручные; `score` и `cosine` не являются вероятностями полезности или покупки.
Штраф/бонус продолжения могут вывести `score` за `[0, 1]`.
Гибрид пока не объединяет semantic и TF-IDF в одной формуле.

Ответ API/CLI содержит `factors` с нормализованными признаками и `score_breakdown`:
веса, подписанные `contributions`, базовую оценку и отдельные штрафы разнообразия,
`selection_score` на момент выбора. Порядок после разнообразия не обязан совпадать
с сортировкой по базовому `score`. `query_vector_source` указывает источник вектора
(запрос, история, fallback). Для числовых JSON-логов в stderr:

```bash
python -m reco.server --ranking-log
python -m reco.cli recommend --task "Продвижение бизнеса в соцсетях" --ranking-log
```

Логи содержат только номер позиции, алгоритм, признаки и вклады. Запросы, история,
названия, ссылки, ID материалов и пользователей не логируются. По умолчанию журнал
выключен; раскладка в API доступна всегда. Спецификация — [ranking-components.md](specs/ranking-components.md).

### Откуда берутся категории

Исходные темы берутся из `ContentSettingsTopics → Topics`, теги — из связей Tags.
У статей при отсутствии тем используется `ArticleSubjects`. Настройки разрешаются
по паре `(EntityId, EntityTypeId)`, а не только по UUID. `Industries` смешивает
отрасли, опыт и редакционные метки, поэтому не считается точной отраслью пользователя.

Если темы нет, близость вектора статьи к векторам названий тем даёт `suggested_topic`.
Это отдельное предположение с cosine и отрывом от второй темы, не замена исходной разметки.
Для `topic_recommendations` считаются центроиды материалов каждой темы и их близость
к текущему вектору пользователя. У гостя без сигналов персональные темы не выдумываются.

## 5. Что сохраняется в интересах пользователя

| Действие | Текущая выдача | Сохранённый профиль |
|---|---|---|
| Задача, поиск `?текст`, онбординг | Влияют | Сами по себе не записываются |
| `click` / `engaged` / `complete` / `dislike` | Влияют при последующих запросах | Обновляют профиль по profile_id |
| Ответ LLM | Добавляет только проверку | Не изменяет |

История зарегистрированного пользователя загружается из PostgreSQL по `user:UserId`.
Гость получает случайный `anon:token`. В JSONB сохраняются ограниченные сведения
о материалах, весах и времени событий, а также последние event_id. Вектор интересов
пересчитывается при запросе; отдельная строка на каждый сырой клик не создаётся.

- Веса событий: click=1, engaged=3, complete=6, dislike=-4.
- Повторные положительные события берут максимальный вес материала, не суммируются бесконечно.
- У новых событий период полураспада 7 дней; история курсов — долгосрочный сигнал.
- До 128 материалов и 256 последних event_id на профиль; дедупликация ограничена этим окном.
- До 10000 гостевых профилей **на fingerprint индекса**; при переполнении вытесняются старейшие.
- TTL гостя: 24 часа без обновлений, максимум 7 дней с момента создания.
  Чтение игнорирует истёкшее состояние сразу; удаление выполняется при записи и API-таймером раз в минуту.
- `cleanup` удаляет истёкших гостей также у старых индексов. У PostgreSQL нет автоматического TTL.
- Зарегистрированные профили без этого TTL; `/merge` переносит ограниченный гостевой профиль
  в зарегистрированный и удаляет гостя. В демо доверие к UserId не проверяется.

Интерфейс отправляет события открытий своих превью и явных отметок пользователя.
Cookie используется только для локального демовхода. Измерения активных секунд на
внешней платформе и проверки личности реального пользователя в MVP нет. События
CLI синтетические; серверная интеграция платформы ещё не выполнена.

## 6. Облачная LLM через API

Основной вариант — **OpenRouter**: один интерфейс для разных моделей, без установки
Ollama. Это посредник, который передаёт запрос выбранному модельному провайдеру.
Для начала можно настроить `openai/gpt-4.1-mini`; наличие нужного маршрута и стоимость
зависят от сервиса. Модель задаётся в окружении, код менять не нужно.
[Быстрый старт OpenRouter](https://openrouter.ai/docs/quickstart),
[страница модели](https://openrouter.ai/openai/gpt-4.1-mini).

При недостаточном локальном контексте LLM получает безопасные признаки задачи, решает необходимость вопроса
и формулирует его. Для этого включите переключатель у строки поиска: `--llm` не нужен.
Вызовы CLI `--llm`/API `use_llm=true` отдельно проверяют карточки. Обычный режим
поиска не обращается к LLM даже при переданном `use_llm=true`.

### Подключение для проверяющего

1. Получите собственный API-ключ в OpenRouter и настройте доступный баланс/лимит.
2. Создайте локальный `.env` по [env.example](env.example), сохранив существующие настройки БД.
3. В `.env` укажите:

```dotenv
LLM_PROVIDER=openrouter
LLM_API_KEY=ВАШ_КЛЮЧ
LLM_MODEL=openai/gpt-4.1-mini
```

Ключ не присылается в браузер, не включается в ответы и не коммитится: `.env` исключён
из Git. Без ключа или модели возвращается `llm_status=disabled`, обычная выдача работает.
Приложение само не покупает кредиты; вызовы по вашему ключу могут тарифицироваться сервисом.

Локальный Python не читает `.env` автоматически. В bash/zsh можно загрузить свой
доверенный файл и выполнить запрос (DATABASE_URL уже должен быть настроен):

```bash
source .venv/bin/activate
set -a
source .env
set +a
python -m reco.cli recommend --task 'Нужно нанять первого сотрудника' --llm -k 3
# Интерактивное демо тоже поддерживает проверку:
python -m reco.cli demo --llm
```

Если индекс построен до появления `llm_public_metadata`, сначала пересоберите его:

```bash
python -m reco.build --backup data/alfa_course_hackathon.backup
```

Старые индексы не считаются разрешением на передачу: обычные рекомендации останутся
доступны, облачная проверка вернёт `privacy_blocked`. После пересборки перезапустите API.

В Docker Compose те же переменные читаются из `.env`; для применения запустите
`docker compose up -d --build recommender`. Для API передайте `"use_llm": true` в
`POST /recommend`. Для CLI нужен `--llm`; одних переменных недостаточно.

### Что действительно уходит в облако

**Исходный запрос и свободные тексты не отправляются вообще.** Вместо попытки
универсально распознать имена/телефоны regex используется фиксированный словарь
бизнес-признаков. Локально из запроса и публичных названий/тем выбираются только
константы вроде «Найм», «Управление командой», «УСН». Описание и тело материала
не используются даже для построения облачной сводки.

Пример содержательной части запроса (синтетические данные):

```json
{
  "task": "Управление командой; Найм",
  "catalog": [
    {"id": "c1", "kind": "course", "summary": "Управление командой; Найм"}
  ]
}
```

В сеть не уходят UserId/anon_id, UUID карточек, контакты, история, ссылки, названия,
аннотации, полные тексты и эмбеддинги. `c1` сопоставляется с настоящим ID только
локально. Допускаются лишь карточки с `llm_public_metadata=true`, установленным
при индексации для доступных опубликованных метаданных. Для статей/курсов/подкастов
нужен известный тип Public/Paid/Subscription; Private/неизвестные типы не допускаются.
Старый флаг без сведений об access также не разрешает передачу. Закрытые карточки
и неизвестное происхождение отбрасываются; IsPublic не заменяет проверку доступа.
Если задача не распознаётся словарём, запрос не отправляется (`no_safe_context`).

Это формат **проверки карточек**. Для **уточнения поиска** каталог вообще не отправляется:
payload содержит фиксированные `topics`, `actions`, `context_hint`, булев `has_history`,
типы доступных форматов и прежние настройки API из констант. Следующий вызов также
получает фиксированные бизнес-признаки ранее сгенерированных пар вопрос/ответ:
темы, канал, уровень, тип формата, укрупнённый диапазон рекламного бюджета.
Полные строки диалога, свободный текст клиента, исходные числа и подписанные токены
в облако не передаются. Даже запрос без распознанной темы
может вызвать LLM-вопрос; его исходный текст не передаётся. Модель возвращает
`needs_clarification` и `question|null`; до 900 выходных токенов. Модель сама пишет
title и 2–5 вариантов label, которые проверяются на форму/дубли/запрос ПДн.
Готовой базы видимых ответов в интерфейсе нет. Без ключа/при ошибке вопроса нет,
`assistant_status` сообщает причину. Выбор передаётся через подписанный токен,
связанный с запросом и предыдущими ответами; срок один час. После перезапуска сервера
начните диалог заново. БД/индекс не меняются, пересборка не нужна.
Повтор уже отвеченного распознаваемого параметра (цель, канал, бюджет, уровень,
формат, аудитория) подавляется локально: `assistant_status=already_answered`.
Тогда сразу показывается подборка с учётом ответа. Эта проверка не распознаёт
все возможные смысловые перефразирования.
Контракт — [specs/dynamic-clarifications.md](specs/dynamic-clarifications.md).
JSON schema использует [Structured Outputs](https://openrouter.ai/docs/guides/features/structured-outputs);
поддержка зависит от выбранного маршрута, поэтому ответ дополнительно проверяется локально.

**Компромисс:** LLM проверяет соответствие общих бизнес-признаков, а не все нюансы
исходной задачи или содержание статьи. Полный локальный запрос всё ещё используется
encoder и математическим ранжировщиком. Нельзя представлять облачную отметку как
экспертную проверку всего материала. Подробный контракт — [specs/cloud-llm.md](specs/cloud-llm.md).

### Транспорт, ответ и ошибки

HTTPS, Bearer-ключ в заголовке, JSON schema ответа; максимум 5 кандидатов,
1200 выходных токенов, 30 секунд ожидания. Автоматических повторов нет, чтобы не
создавать повторные расходы. HTTP-переадресации запрещены, ключ на другой адрес
не переносится. Для OpenRouter задаются `data_collection=deny`, `zdr=true`,
`require_parameters=true`; при отсутствии подходящего маршрута политика не ослабляется.
[Политика маршрутизации](https://openrouter.ai/docs/guides/routing/provider-selection).
У сервиса есть исключения Safety Retention: для строгого ZDR дополнительно проверьте
настройки аккаунта. Параметры маршрутизации не заменяют нашу минимизацию данных.

Ответ принимается только для отправленных псевдонимов, с настоящим boolean и
точной цитатой из безопасного `summary`. Неизвестные ID, дубли, выдуманные цитаты
и слишком длинное основание отбрасываются. В карточке: `source=cloud_llm`,
`basis=controlled_summary`, `llm_checked=true`. Это не цитата из полного материала.

| llm_status | Значение |
|---|---|
| `ok` | Приняты проверки всех отправленных карточек |
| `partial_privacy_filter` | Проверена лишь разрешённая часть/первые 5 карточек |
| `partial_invalid_output` | Часть ответа не прошла локальную проверку |
| `privacy_blocked` | Нет разрешённых карточек/старый индекс без флага |
| `no_safe_context` | Задача не преобразуется в допустимые признаки |
| `disabled` | Нет ключа/модели либо проверка выключена |
| `invalid_endpoint` / `invalid_provider` | Ошибка настройки |
| `authentication_or_policy_error` / `rate_limited` | Отказ доступа/политики либо лимит сервиса |
| `provider_error` / `unavailable_or_invalid_output` | Ошибка API, сети, JSON или тайм-аут |
| `invalid_output` | Ответ превышает лимит или имеет неподходящую структуру |

Сбой сохраняет обычную выдачу. LLM не переставляет и не удаляет карточки; даже
`relevant=false` пока только флаг. Ответ не меняет профиль интересов, история
диалога не передаётся. Проверка истинности/актуальности законов не выполняется.
Без ключа внешние вызовы не делаются. В тестах транспорт перехватывается;
проверка живого OpenRouter с предоставленным владельцем ключом описана ниже.

### Другой совместимый API и прежняя Ollama

Для совместимого Chat Completions сервиса задайте `LLM_PROVIDER=compatible`,
`LLM_BASE_URL=https://адрес-сервиса/v1`, `LLM_API_KEY` и его `LLM_MODEL`.
Base URL — без `/chat/completions`, без credentials/query/fragment, только HTTPS.
Нужна модель с поддержкой JSON schema; специфичные параметры OpenRouter не передаются.
Политика хранения другого сервиса проверяется отдельно. Наш безопасный экспорт тот же.
[Формат Chat Completions](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create).

Локальная Ollama поддерживается при `LLM_PROVIDER=ollama`, `OLLAMA_URL` и `OLLAMA_MODEL`.
В ней сохранён прежний формат: задача до 1000 символов и название/аннотация до
700 символов/темы выбранных материалов, исходные ID. Этот путь допускает только
localhost/loopback/host.docker.internal и не считается облачным безопасным экспортом.
Если LLM_PROVIDER не задан, старые OLLAMA-настройки без нового API-ключа выбирают
локальный путь; иначе по умолчанию выбирается OpenRouter.

## 7. HTTP API

POST принимает `Content-Type: application/json` (иначе 415). Браузерные изменения
доступны только со страницы этого локального HTTP-сервиса; чужой/null Origin
отклоняется с 403 до вызова LLM и записи данных. CLI без Origin поддерживается.
Это не заменяет авторизацию при внешнем размещении.

Локальный запуск: `python -m reco.server`. Адрес по умолчанию `127.0.0.1:8000`;
доступны `--host`, `--port`, `--artifacts`. Базовый демонстрационный API предназначен
для локального демо. `UserId` из запроса не подтверждает личность.

| Метод и путь | Назначение |
|---|---|
| `GET /` | Веб-интерфейс «Умного поиска» |
| `GET /health` | Состояние, backend и размер доступного каталога |
| `GET /catalog?limit=20` | Первые карточки каталога, не персональная выдача; limit от 1 до 100 |
| `POST /profiles` | Возвращает случайный гостевой profile_id; запись создаётся после события |
| `POST /recommend` | Подбор по задаче, профилю, темам и онбордингу |
| `POST /search` | `search_mode=normal` (по умолчанию) или `smart`; обычный/умный поиск |
| `POST /smart-search` | Совместимый адрес с режимом `smart` по умолчанию |
| `POST /events` | Обновление интересов, timestamp задаёт сервер |
| `POST /merge` | Демонстрационная привязка гостя к user:UserId |
| `DELETE /profiles/<profile_id>` | Удаление агрегата этого профиля у текущего индекса |
| `GET /demo/accounts` | Готовые синтетические роли и число стартовых действий |
| `GET /demo/session` | Текущий демовход по cookie, без токена в JSON |
| `POST /demo/login` | `{account_id}`: отдельная тестовая копия и HttpOnly cookie |
| `POST /demo/logout` | `{}`: отзыв сессии, удаление её копии, очистка cookie |
| `POST /demo/reset` | `{}`: восстановление стартовых тестовых действий своей сессии |

Пример запроса:

```bash
curl -X POST http://127.0.0.1:8000/recommend \
  -H 'Content-Type: application/json' \
  -d '{"task":"Как управлять командой","profile_id":"anon:demo","topics":["Управление командой"],"k":5}'
```

В `/recommend` также поддерживаются `stage`, `industry`, `experience`,
`preferred_format`, `algorithm` (`topic`, `cosine`, `hybrid`), `use_llm`, `include_continuations`.
`k` — целое 1–20. Ответ содержит режим, темы, факторы, исходную ссылку/slug,
цену (`null` — неизвестна), объяснение и следующий шаг. Общий домен к slug
`/recommend` не дописывает; `/smart-search` добавляет `material_url` по маршрутам
платформы, не гарантируя актуальность каждой страницы. Неизвестные маршруты дают 404, ошибки аргументов — 400,
слишком большое тело POST — 413, внутренний сбой — 500.

Возьмите `id` карточки из ответа, замените `ID_ИЗ_ВЫДАЧИ` и отправьте событие:

```bash
curl -X POST http://127.0.0.1:8000/events \
  -H 'Content-Type: application/json' \
  -d '{"profile_id":"anon:demo","item_id":"ID_ИЗ_ВЫДАЧИ","event_type":"engaged","event_id":"demo-001"}'
```

Повтор этого event_id в пределах последних 256 не усиливает профиль повторно.
Удаление агрегата через API не удаляет исторические записи на курсы из источника.
Ручная очистка просроченных гостей: `python -m reco.cli cleanup` — индекс и модель не нужны.

При демовходе `/search`, `/smart-search`, `/recommend` и `/events` используют профиль
из сессии. Переданный иной `profile_id` → 403; демо-ID без своей сессии → 401.
Демопрофили нельзя объединять через `/merge`. Обычные CLI/API-сценарии сохранены:
демовход не добавляет production-аутентификацию исходным `user:UUID` из backup.

Последний полный прогон 16 ноября: **151 тест** на отдельной PostgreSQL без пропусков,
включая перенос готовых эмбеддингов, startup и регрессию гонки event/expiry.
Восстановление настоящего `.backup` в отдельную временную БД заняло **4,611 с**
на этой машине: 1126 × 1024, 10 032 записи истории, 7339 пользователей. Каталог,
encoder, темы и обе матрицы побайтно совпали с исходным индексом; fingerprint сохранён.
`Encoder.fit/encode` во время проверки запрещены; вызовов модели и LLM — ноль.
Это время восстановления без скачивания весов, не замер первого Docker-старта.
В тестах ответы провайдера перехватываются, платных запросов нет. Дополнительная
проверка на настоящем каталоге подтвердила псевдонимы, фильтр допустимости,
отсутствие свободного текста в payload и сохранение математического порядка.
15 ноября выполнены реальные вызовы OpenRouter с `openai/gpt-4.1-mini`: HTTP 200,
LLM-вопрос в браузере, подборка после ответов и проверка трёх карточек (`llm_status=ok`,
все три `llm_checked=true`). Это короткая интеграционная проверка, не оценка общего
качества диалога. Ключ хранится только в локальном игнорируемом `.env`, в Git его нет.

```text
artifacts/
  current -> .generations/index-.../
  .generations/index-.../
    catalog.json        # карточки, eligibility, флаг публичных метаданных для LLM
    vectors.npy         # векторы материалов
    topics.json         # названия тем
    topic_vectors.npy   # центроиды тем
    encoder.json        # backend, модель/revision или словарь/IDF
    audit.json          # количества, исключения, fingerprint
    manifest.json       # контрольные суммы файлов
models/huggingface/      # локальный кеш модели
precomputed/bge-m3/      # готовые числовые матрицы, encoder и manifest в Git
PostgreSQL: reco.datasets, reco.history, reco.profiles
```

Индекс публикуется после импорта истории и проверки файлов, переключением ссылки
`current`. Потребитель фиксирует одно поколение при загрузке. Ошибка сборки оставляет
предыдущее активным. Старый плоский индекс поддерживается; без тем файл центроидов
может отсутствовать. Для новых поколений manifest требует все файлы.
PostgreSQL и файловая система не составляют единую транзакцию: после отказа публикации
неактивные данные fingerprint могут остаться в БД, но старый файловый индекс остаётся рабочим.

Файлы SQLite могут остаться от раннего прототипа, текущий код их не использует.
Дампы, модели, артефакты, `.env` и пользовательские данные исключены из Git и Docker
build context. Единственное исключение — четыре файла числового набора
`precomputed/bge-m3/`. Не публикуйте исходные выгрузки и копии контента/истории.

## 9. Проверки и оценка качества

Для полного прогона создайте отдельную тестовую БД. Например, с PostgreSQL из Compose
(создание `reco_test` выполняется один раз):

```bash
docker compose exec postgres createdb -U reco reco_test
export TEST_DATABASE_URL='postgresql://reco:local-demo-only@localhost:5433/reco_test'
python -m unittest discover -s tests -q
```

Без `TEST_DATABASE_URL` тесты PostgreSQL пропускаются — это не полный зелёный прогон.
Не указывайте в этой переменной рабочую БД. Fixtures изолированы случайными dataset.
При работающем API выполните `python scripts/smoke_api.py`: проверяются стартовая
выдача, событие, дедупликация, новая выдача, некорректный запрос и удаление тестового гостя.

Оценка рекомендаций требует DATABASE_URL и подготовленного индекса:

```bash
python -m reco.evaluate --output artifacts/evaluation.json
python -m reco.evaluate --artifacts artifacts-tfidf --output artifacts-tfidf/evaluation.json
```

Метрики: Precision@5, NDCG@5, покрытие каталога, время после прогрева.
[evaluation/profiles.json](evaluation/profiles.json) — **пять синтетических сценариев
с черновой неполной разметкой автора**, реальные ID материалов. Неоценённые материалы
считаются нерелевантными; результаты не доказывают качество на реальных пользователях
или рост покупок. В историческом прогоне до текущих изменений TF-IDF-гибрид показал
NDCG@5 0.5496, семантический гибрид — 0.4694; это отдельный прежний запуск.
В сопоставимом прогоне 15 ноября на одном каталоге и истории, до hybrid-v2:

| Encoder / метод | Precision@5 | NDCG@5 |
|---|---:|---:|
| Темы + популярность (оба encoder) | 0.12 | 0.0810 |
| ruBERT / косинус | 0.24 | 0.3668 |
| ruBERT / гибрид | 0.36 | 0.4651 |
| BGE-M3 / косинус | 0.36 | 0.5789 |
| BGE-M3 / гибрид | 0.44 | 0.5458 |

Эти числа относятся к прежним весам. Качество hybrid-v2 отдельно не измерялось;
новые веса заданы вручную, seed-профили для их подбора не использовались.

BGE-M3 на CPU: p50 111 мс, p95 2010 мс для 15 кодирований коротких запросов
длиной 10–17 токенов. Условия: Mac arm64, 8 ГиБ RAM, float32, два потока PyTorch;
это **не измерение на Windows**. Индекс из настоящего backup пересобран: 1126×1024
конечных нормализованных векторов. API после сборки проверен с устройством CPU.
Первичная индексация на MPS заняла около 42 минут, не считая скачивания весов;
холодный запуск на другой машине может занять другое время.
Подробности и воспроизведение — [сравнение encoder](docs/embedding-comparison.md).
Это повторная проверка движка на известных сценариях, не оценка эффекта интерфейса
или независимый контроль. Нужны расширенная разметка и отдельная итоговая выборка.

Реальная проверка 14 ноября 2026: 47 тестов на отдельной PostgreSQL прошли без пропусков,
семантический API и сценарии с настоящей историей работали. Количества всех 62 таблиц
восстановленной БД сверены с `.backup`; поля каталога и производная история — с повторной
обработкой дампа. Векторы 1126×312 конечны, нормы около 1. Это не построчное сравнение
всех значений во всех исходных таблицах. Подробности:
[отчёт запуска](coordination/attempts/2026-11-14-live-run.md),
[ревью исправления](coordination/reviews/2026-11-14-legacy-verifier.md),
[контракт хранения](specs/postgresql-storage.md).

## 10. Типичные ошибки и границы MVP

| Симптом | Что проверить |
|---|---|
| Требуется DATABASE_URL | Экспортируйте URL в текущем терминале; локальный Python не читает .env автоматически |
| Connection refused | БД запущена? Compose использует порт 5433 с хоста, внутри сети — postgres:5432 |
| pg_restore не найден / версия архива не поддержана | Установлен и доступен клиент PostgreSQL 17+ |
| История индекса не импортирована | Выполните reco.migrate для того же --artifacts и DATABASE_URL |
| Existing artifacts use a different backend | Разделите каталоги semantic и TF-IDF или явно пересоберите нужный индекс |
| Fingerprint/manifest/NaN ошибка | Восстановите согласованное поколение или пересоберите; не правьте файлы индекса вручную |
| Модель не загружается | Первая сборка требует сети, следующие запросы — сохранённой revision в локальном кеше; автоматического fallback нет |
| Порт 8000 занят | Остановите свой предыдущий сервер либо выберите --port для Python |
| NotOpenSSLWarning | Предупреждение окружения старого системного Python/LibreSSL; используйте совместимую сборку Python или Docker, это не traceback приложения |

В MVP нет измерения активных секунд на платформе,
реальной авторизации и обучения вероятности покупки. Отдельный запрос не становится
устойчивым интересом без события. Encoder может путать близкие слова при
разных намерениях; LLM пока только помечает результаты. В API операции одного движка
сериализованы — нагрузочная готовность не доказана. Нет автоматической очистки всех
старых поколений, историй и зарегистрированных профилей.

Для проверки бизнес-эффекта после внедрения нужен A/B-тест с устойчивым распределением
пользователей: главная метрика — подтверждённая покупка, дополнительные — регистрация,
возвраты и активные дни. Сейчас журнал показов и достоверные purchase-события отсутствуют,
поэтому рост конверсии не заявляется. Также для конкурсной сдачи нужна отдельная PDF-презентация.

Правила совместной работы — [AGENTS.md](AGENTS.md), решения и отчёты — [coordination/](coordination/).
