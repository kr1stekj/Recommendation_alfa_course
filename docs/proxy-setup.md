# Подключение прокси

Прокси необязателен: он нужен, если контейнер не может напрямую обращаться к
OpenRouter. Он не исправляет неверный API-ключ, отсутствие баланса или лимит модели.
Для подключения нейросети по-прежнему нужен отдельный ключ OpenRouter.

## 1. Получить параметры

У поставщика прокси выберите HTTP-прокси с поддержкой HTTPS через CONNECT.
Для обычного подключения Docker удобен доступный по IPv4 адрес. Не выбирайте
IPv6-only вариант, если не проверена поддержка IPv6 в вашей сети и Docker.
SOCKS-прокси этой конфигурацией не поддерживается.

После выдачи прокси получите четыре значения:

| Параметр | Пример, не рабочие реквизиты |
|---|---|
| Адрес | `proxy.example.com` |
| Порт | `8080` |
| Логин | `demo_user` |
| Пароль | `demo_password` |

Уточните у поставщика: разрешены ли HTTPS CONNECT, нужные внешние сервисы,
подключения из вашей сети и сколько одновременно подключений допускается.
Прокси с привязкой к IP потребует разрешить внешний IP компьютера проверяющего;
для переносимой демонстрации удобнее авторизация логином и паролем.
Конкретный поставщик/страна не гарантируют доступность OpenRouter.

## 2. Записать в .env

Откройте `.env` в корне проекта, рядом с `compose.yaml`. Если файла нет,
скопируйте `env.example` в `.env`. Не создавайте второй файл с именем `.env.txt`:
на Windows проверьте отображение расширений файлов.

Добавьте или замените одну строку:

```dotenv
RECO_PROXY_URL='http://demo_user:demo_password@proxy.example.com:8080'
```

Общий формат:

```text
http://ЛОГИН:ПАРОЛЬ@АДРЕС:ПОРТ
```

`http://` здесь означает протокол подключения к самому прокси. Запросы к
OpenRouter остаются HTTPS: используется туннель CONNECT с проверкой TLS.
Не отключайте проверку сертификатов для устранения ошибок соединения.

Если в логине или пароле есть специальные символы, кодируйте каждый компонент
URL отдельно: `@` → `%40`, `:` → `%3A`, `#` → `%23`, `%` → `%25`, пробел → `%20`.
Например, пароль `demo@pass` записывается как `demo%40pass`. Не кодируйте разделители
самого адреса (`http://`, двоеточие перед портом и `@` между реквизитами и хостом).
Одинарные кавычки вокруг значения сохраняют буквальный `$` для dotenv Compose.

Ключ и модель указываются независимо:

```dotenv
LLM_PROVIDER=openrouter
LLM_API_KEY=YOUR_OPENROUTER_KEY
LLM_MODEL=openai/gpt-4.1-mini
```

Все значения выше демонстрационные. Рабочие настройки команда хранит в локальном
текстовом файле; перенесите оттуда соответствующие строки в свой `.env`.

## 3. Применить настройки

При первом запуске из корня проекта:

```bash
docker compose up --build
```

Если приложение уже запускалось, после изменения `.env` пересоздайте контейнер:

```bash
docker compose up -d --force-recreate recommender
```

Простого `docker compose restart` недостаточно для загрузки новых переменных.
Пересчитывать эмбеддинги и удалять тома БД не требуется.

Compose передаёт настройку в HTTP_PROXY/HTTPS_PROXY и их lowercase-варианты
только контейнеру приложения. PostgreSQL, localhost, 127.0.0.1, IPv6 loopback и
host.docker.internal обходят прокси. Эта настройка не является настройкой
Docker daemon или загрузки базовых образов: если падает `docker pull`/сборка
до запуска приложения, отдельно проверьте сеть и настройки Docker Desktop.

## 4. Проверить без расходования LLM-запросов

Убедитесь, что контейнер приложения запущен. Выполните команду ниже целиком:

```bash
docker compose exec recommender python -c "import urllib.request; p=urllib.request.getproxies(); print('HTTPS proxy configured:', bool(p.get('https'))); r=urllib.request.urlopen('https://openrouter.ai/api/v1/models', timeout=20); print('OpenRouter connectivity:', r.status); r.close()"
```

Она запрашивает публичный список моделей, не отправляет API-ключ, пользовательский
запрос или каталог и не запускает генерацию LLM. Реквизиты прокси не печатаются.
Ожидается `HTTPS proxy configured: True` и `OpenRouter connectivity: 200`.
Это проверка сети до OpenRouter, а не баланса, ключа или работоспособности выбранной
модели. Без настроенного прокси первое значение будет False; ответ 200 тогда
показывает доступность сервиса напрямую.

Не публикуйте полный вывод `docker compose config`: в нём могут быть секреты.
Команда проверки выше при сетевом сбое выдаст исключение; не пересылайте вывод,
не проверив, что в нём нет ваших реквизитов.

## 5. Если не работает

| Симптом | Что проверить |
|---|---|
| `HTTPS proxy configured: False` | Имя `.env`, расположение рядом с Compose, непустой RECO_PROXY_URL, пересоздание контейнера |
| `407 Proxy Authentication Required` | Логин, пароль, кодирование спецсимволов, способ авторизации у поставщика |
| Timeout / connection refused | Адрес, порт, срок действия, доступность прокси из сети, лимит подключений |
| Публичный список моделей доступен, но LLM нет | Ключ OpenRouter, доступ к модели, баланс/квоту; прокси сам по себе их не предоставляет |
| Ошибка TLS | Системное время и доверенные сертификаты, отсутствие подмены TLS; не отключать проверку |
| Не скачивается Docker-образ | Сеть/Docker Desktop: RECO_PROXY_URL не настраивает Docker daemon |

Для отключения оставьте в `.env`:

```dotenv
RECO_PROXY_URL=
```

Затем снова выполните `docker compose up -d --force-recreate recommender`.
Локальный Python вне Docker не получает этот прокси автоматически: эта инструкция
описывает основной Docker-вариант запуска проекта.
