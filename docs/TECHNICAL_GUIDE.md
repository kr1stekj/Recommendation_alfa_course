# Документация прототипа «Альфа-Курс»

Трек 1, команда «Майёвтика». Назначение: подбирать материалы каталога под задачу
предпринимателя, объяснять выбор и учитывать взаимодействия без обязательной регистрации.
Это прототип, а не официальная платформа Альфа-Банка.

## Архитектура и входные данные

| Компонент | Назначение | Код |
|---|---|---|
| Подготовка | Чтение предоставленного PostgreSQL backup, очистка полей | `reco/data.py`, `reco/missing.py` |
| Индекс | Каталог, плотные векторы и тематические центроиды | `reco/index.py`, `reco/precomputed.py` |
| Encoder | Локальная BAAI/bge-m3, 1024 координаты, L2, окно 512 | `reco/embeddings.py` |
| Рекомендации | Профиль, кандидаты, оценки, разнообразие | `reco/engine.py`, `reco/feed.py`, `reco/ranking.py` |
| Диалог | Уточнение задачи и проверка выбранных вариантов | `reco/search.py`, `reco/clarification.py`, `reco/dialog.py` |
| Хранилище | PostgreSQL: производная история и агрегаты профилей | `reco/database.py`, `reco/state.py` |
| Интерфейс/API | Локальный HTTP-сервер и браузерный UI | `reco/server.py`, `reco/web/` |

Дамп `data/alfa_course_hackathon.backup` предоставляют организаторы; его нет в Git.
Готовый индекс содержит 1126 материалов, 1115 доступны для выдачи, 26 тематических
меток. Производная история: 10032 записи, 7339 пользователей. Это характеристики
подготовленного набора, не число пользователей прототипа. Пропуски NULL/NaN/\\N,
HTML и некорректные значения нормализуются; недоступные карточки исключаются.

В репозитории есть готовые числовые векторы; при запуске проверяется их совместимость
с дампом и настройками. Веса encoder около 2,3 ГБ скачиваются отдельно для новых
запросов. NumPy-поиск по матрице достаточен для текущего объёма; отдельной векторной
БД и обученного reranker нет. Docker-тома сохраняют БД, индекс и кеш модели.

## Как формируется выдача

1. При пустой строке в обоих режимах показывается лента: обычно 8 персональных,
   1 популярный и 1 ознакомительный материал; в малом каталоге квоты сокращаются.
2. Обычный непустой поиск ищет лексически без персонального диалога.
3. Умный поиск выделяет текущую задачу и сначала отбирает подходящих кандидатов.
   Вектор текущего запроса имеет 90%, нормализованный вектор истории — 10%.
   Старый `/recommend` сохраняет отдельный режим 75/25.
4. При недостаточном контексте LLM может сформулировать вопрос и 2–5 ответов
   в блоке поиска. Максимум два уточнения, их можно пропустить. Ответы подписаны
   сервером и привязаны к запросу; произвольный текст клиента не считается ответом.
5. Материалы возвращаются только из допустимого каталога: название, ID/ссылка,
   объяснение и следующий шаг. LLM не дописывает новые карточки в базу.

Гибридная оценка:

```text
0.75*cosine + 0.16*topic + 0.04*format + 0.05*popularity
- 0.12*dislike + 0.03*continuation
```

Компоненты гибрида ограничены [0,1], cosine = max(0, cosine). Тема берётся из
меток каталога, популярность — нормализованный log(1+count). При отсутствии
формата/популярности/dislike вклад нулевой. Score не является вероятностью.
Разнообразие обычного hybrid учитывается мягкими штрафами; стартовая лента
использует взвешенное распределение тем. До четырёх доступных положительных тем
сначала получают представительство, остальные места зависят от приоритета.
Все метки равноправны; карточка с несколькими метками не дублируется.
Подробности: [ранжирование](../specs/ranking-components.md),
[приоритет запроса](../specs/search-intent-priority.md),
[свежесть](../specs/interest-recency.md).

## Профиль, события и очистка

Поиск и ответы меняют текущий контекст, но сами не записывают постоянный интерес.
Открытие окна карточки отправляет click; кнопки «Полезно», «Уже изучил» и
«Не подходит» — engaged/complete/dislike. Их базовые веса: 1/3/6/-4.
Автоматического измерения времени на внешней странице курса нет.

Повторные клики не наращивают вес бесконечно, но настоящий новый клик обновляет
время. Дубликат event_id этого не делает в пределах последних 256 ID.
В профиле до 128 материалов, а не отдельная строка на каждый клик.
Положительный live-вес уменьшается вдвое за сутки, отрицательный — за 7 дней.
Приоритет темы ленты: sqrt(сумма положительных затухших весов)/(1+rank последней
активности). Равные даты имеют одинаковый rank. Импортированная история остаётся
долгосрочной, поскольку её актуальные даты неизвестны.

ID гостя находится в localStorage, агрегат — в PostgreSQL. Гостевые профили удаляются
после 24 часов бездействия либо 7 дней общего возраста; лимит 10000 гостей на dataset.
Есть периодическая и ленивая очистка. Кнопка удаления относится к текущему профилю;
демо-сессия сбрасывается отдельно. Демовход выбирает синтетический профиль без
регистрации/пароля и создаёт отдельную тестовую копию.

## OpenRouter: получение и подключение ключа

1. Зарегистрируйтесь на [OpenRouter](https://openrouter.ai/).
2. На странице [API Keys](https://openrouter.ai/keys) создайте ключ и сохраните его.
3. Проверьте доступность выбранной модели и баланс/лимиты аккаунта.
   Бесплатные модели имеют свои ограничения и не гарантируют доступность.
4. Скопируйте `env.example` в `.env`, сохранив существующие настройки, и заполните:

```dotenv
LLM_PROVIDER=openrouter
LLM_API_KEY=YOUR_OPENROUTER_KEY
LLM_MODEL=openai/gpt-4.1-mini
```

Нужен ключ OpenRouter, а не отдельный ключ OpenAI: `openai/gpt-4.1-mini` —
идентификатор модели у агрегатора. Источники: [официальная инструкция разработчика](https://openrouter.ai/developers),
[поддержка OpenRouter](https://openrouter.ai/support/).

Подробная [инструкция по прокси](proxy-setup.md): получение параметров, `.env`,
перезапуск и проверка без LLM-запросов.

Прокси необязателен. Если сеть требует его, получите у выбранного поставщика
HTTP-прокси с поддержкой HTTPS CONNECT и реквизиты: host, port, user, password.
Конкретный поставщик не обязателен, доступность OpenRouter через него не гарантируется.
Добавьте в `.env`:

```dotenv
RECO_PROXY_URL='http://USER:PASSWORD@HOST:PORT'
```

Спецсимволы логина/пароля кодируются как компоненты URL. Пустое значение отключает
прокси. Compose передаёт его только приложению; loopback IPv4/IPv6, PostgreSQL и
host.docker.internal обходят прокси. Для локального Python эта Compose-настройка
не применяется автоматически. После смены настроек контейнера:

```bash
docker compose up -d --force-recreate recommender
```

Ключ остаётся на сервере. Во внешний API уточнений передаются фиксированные
бизнес-признаки, а не исходная строка, ID, журнал действий или закрытые материалы.
Минимизация может терять нюансы запроса. Отдельная необязательная проверка карточек
не меняет порядок математической выдачи. При недоступности LLM остаются локальные
рекомендации с явным сообщением; вопросы не подменяются статической базой.

## HTTP API

Сервер: `http://127.0.0.1:8000`. PostgreSQL с хоста:5433, внутри Compose:5432.

| Метод и путь | Назначение |
|---|---|
| `GET /health` | Состояние приложения/индекса |
| `POST /profiles` | Создать гостевой профиль |
| `POST /search` | Поиск, по умолчанию normal |
| `POST /smart-search` | Поиск, по умолчанию smart |
| `POST /recommend` | Прямой вызов рекомендательного движка |
| `POST /events` | Действие с карточкой, дедупликация event_id |
| `DELETE /profiles/<id>` | Удаление профиля по переданному ID |
| `GET /demo/accounts`, `GET /demo/session` | Профили демонстрации/состояние сессии |
| `POST /demo/login`, `/demo/logout`, `/demo/reset` | Управление демо-сессией |

Пример тела поиска после создания профиля (подставьте его фактический ID):

```json
{"task":"статьи про ИИ","profile_id":"anon:YOUR_PROFILE_ID","search_mode":"smart","skip_questions":true}
```

Пример события с новым уникальным event_id и существующим ID из выдачи:

```json
{"profile_id":"anon:YOUR_PROFILE_ID","item_id":"article:ITEM_ID","event_type":"click","event_id":"UNIQUE_EVENT_ID"}
```

ID в примерах — placeholders. Демо-сессии используют cookie; нельзя произвольно
подменять её профиль. У гостя случайный ID не заменяет промышленную авторизацию:
знание ID даёт доступ к операциям с ним. Прототип рассчитан на локальную проверку.
Контракты полей/валидации: [JSON Schema](../specs/smart-search.schema.json),
[динамические уточнения](../specs/llm-clarification.schema.json). Пути здоровья и
каталога не заменяют проверку основного пользовательского сценария.

## Сценарий проверки и известные ограничения

1. Запустить по README, дождаться готовности, открыть интерфейс.
2. Без входа проверить стартовую ленту и обычный текстовый поиск.
3. Включить умный режим: конкретная задача даёт подборку; общая может вызвать
   уточнение при доступной LLM. Выбрать ответ либо пропустить вопрос.
4. Открыть карточки двух тем, обновить страницу: интересы сохраняются, свежесть
   влияет на распределение, обе темы могут остаться представлены.
5. Отметить материал изученным/неподходящим, проверить исключения из рекомендаций.
6. Войти в демопрофиль, сменить его, выйти; проверить разные стартовые контексты.
7. Удалить текущую историю; убедиться, что сброшен нужный гостевой профиль.

Регрессии запускаются `python -m unittest discover -s tests -q` после установки
зависимостей. Для PostgreSQL-тестов задайте TEST_DATABASE_URL на отдельную тестовую
БД; без него часть проверок пропускается. Не используйте рабочую БД для тестов.
Не запускайте платные LLM-вызовы ради повторной проверки документации.

Ранее прошли 184 теста алгоритма и адресная регрессия proxy bypass. Docker ARM64/
AMD64 собирался на более раннем снимке, ARM64 запускался. Windows runtime и
Docker-запуск последнего main здесь не подтверждены. Метрики пяти синтетических
профилей исторические, с неполной разметкой; итоговая независимая оценка отсутствует.
Ссылки каталога могут устаревать. Весовые коэффициенты — эвристика, не оптимум.
Рост конверсии не доказан: предложен A/B-тест с основной метрикой покупки курса/
подписки и дополнительными CTR/началом обучения/возвратами.
